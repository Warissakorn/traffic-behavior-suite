# จับคู่รถข้ามจุดและต้นทาง–ปลายทาง (Observed OD)

ใช้จับคู่รถคันเดิมจาก **หลายกล้อง** หรือ **กล้องเดียวที่ย้ายตำแหน่งและบันทึกคนละเวลา**
โดยแยกชื่อกล้องออกจากจุดสังเกตและช่วงสำรวจ เช่น กล้อง 1 ถ่ายที่ A เวลาเช้า
แล้วไปถ่ายที่ B ภายหลัง ให้สร้างสองช่วงสำรวจที่มี `point_id` A และ B
เวลาเดินทางต้องเป็นไปได้จริงตามลำดับเวลา จึงจะเสนอให้จับคู่

ผล OD หมายถึง **จุดแรกและจุดสุดท้ายที่พบในข้อมูลที่นำเข้า**
ไม่ใช่บ้าน จุดเริ่มทริป หรือจุดจบทริปจริงของรถ การไม่พบรถในอีกจุดไม่ได้แปลว่ารถจบการเดินทาง
รถที่ยังไม่มีคู่ยืนยันยังอยู่ใน `sightings.csv` และไม่นับในตาราง OD

## ภาพต่างมุม ไม่มีทะเบียน และไม่มีการติดตามต่อเนื่อง

ค่าเริ่มต้น **ภาพ + เวลา (`identity_mode: independent`)** มองรถที่พบ ณ A/B
เป็นรายการสังเกตแยกกัน ไม่กำหนดว่าต้องมี Track ID เดียวกันระหว่างจุด
จึงเสนอคู่ได้แม้รถหายไปหลายนาทีหรืออยู่ในวิดีโอเดียวกันแต่ ID เปลี่ยน
ID ภายในแต่ละจุดใช้รวมภาพตัวอย่างของรายการนั้น ไม่ใช่หลักฐานตัวตนระหว่างจุด
ยังต้องมีผลวิเคราะห์ในแต่ละจุดเพื่อสร้างรายการรถและเวลา แต่ไม่ต้องมีการติดตามตลอดทาง A→B

ไม่บังคับป้ายทะเบียน เมื่อไม่มีป้ายให้ใช้ appearance, ประเภท และช่วงเวลาเดินทาง
โมเดล Vehicle Re-ID ที่ฝึกกับภาพรถหลายมุมช่วยได้ แต่ภาพด้านหน้ากับท้ายรถ
อาจไม่มีรายละเอียดร่วมกันพอ โดยเฉพาะรถสี/รุ่นเดียวกัน แสงต่างกัน หรือภาพไม่ชัด
ความคล้ายจากสีอย่างเดียวไม่เพียงพอที่จะยืนยันรถในกรณีเหล่านี้
adapter ONNX ไม่ได้พิสูจน์ว่าโมเดลหรือค่า threshold ใดแม่นยำกับกล้องจริงแล้ว

ในแท็บตรวจคู่ เลือกรถต้นทางจาก dropdown เพื่อดู Candidate เรียงตามความคล้าย
และสลับดูภาพตัวอย่างได้สูงสุดสามเฟรมต่อฝั่ง พร้อมเวลาของแต่ละภาพ
เลือกยืนยันคู่ ปฏิเสธ รอตรวจ หรือ **ไม่พบคู่ใน Candidate**
ตัวเลือกไม่พบคู่บันทึกผลแยกจากรถที่ยังไม่ตรวจ ไม่ถือเป็นหลักฐานว่ารถจบการเดินทางที่จุดนั้น
ถ้ามีคู่ยืนยันอยู่ ต้องถอนคู่เดิมก่อนระบุไม่พบคู่ ทุกคู่เริ่มรอตรวจ ไม่มีการยืนยันอัตโนมัติ
OD ใช้เฉพาะคู่ที่คนยืนยันแล้ว คู่ที่คะแนนใกล้กันแสดงว่ากำกวมและสามารถพักไว้ได้

โหมด **ใช้ Track ID เดียวกัน (`shared_track`)** ยังเลือกใช้ได้เมื่อมีการติดตามต่อเนื่องจริง
เท่านั้น หากต้องการจับคู่หลังหลุด ID ให้ใช้ `independent` ไม่เพิ่มช่วงขาดการติดตามเป็นหลายนาที

## ใช้จากโปรแกรม

1. วิเคราะห์แต่ละจุดผ่านหน้าจุดสำรวจให้เสร็จ โดยใช้ calibration ของตำแหน่งนั้น
   และ `videos[].start_time` ที่มีวันที่ เวลา และ timezone จริง
   หน้า “ทดสอบวิดีโอ” ให้เฉพาะ detection จึงยังนำมาใช้เป็นรถรายคันไม่ได้
2. เปิดเมนู **จับคู่รถ / OD** แล้วกด **เพิ่มผลวิเคราะห์จุดสำรวจ**
   เลือกโฟลเดอร์ run ที่มี `manifest.json`, `vehicles.parquet`, `detections.parquet`,
   `frames.parquet` และ `config.resolved.json` ต้องเก็บวิดีโอต้นทางไว้เพื่อสร้างภาพรถ
3. ตั้ง **ช่วงสำรวจ ID** ให้ไม่ซ้ำและ **จุดสังเกต** ให้ตรงตำแหน่งจริง
   กล้องเดียวที่ย้ายตำแหน่งให้ใช้ชื่อจุดต่างกัน ถ้าจุดเดิมแต่คนละช่วงเวลาให้ใช้
   จุดเดียวกันแต่ช่วงสำรวจ ID ต่างกัน และนำเข้าคนละ run
   หรือเลือกจุดผ่านต่างกันจาก run เดียวกันตามขั้นตอนท้ายเอกสาร
4. กำหนด **ชดเชยนาฬิกา** เป็นวินาที: เวลาที่ใช้จับคู่ = เวลาในผลวิเคราะห์ + ค่านี้
   เช่น นาฬิกากล้องช้า 30 วินาที ให้ใส่ `30` ระบบไม่ประมาณ offset/drift ให้อัตโนมัติ
5. เพิ่ม **เส้นทาง** แบบมีทิศ เช่น A→B และ B→C พร้อมเวลาเดินทางต่ำสุด/สูงสุด
   หน่วยวินาที วัดจากเวลาที่พบรถครั้งสุดท้ายที่ต้นทาง ถึงครั้งแรกที่ปลายทาง
   ไม่ได้ใช้ระยะทางพิกเซลระหว่างกล้อง และไม่ใช้ FPS สมมติแทนเวลาจริง
6. กด **จับคู่รถข้ามจุด** ระบบทำงานเบื้องหลัง แสดงความคืบหน้าและยกเลิกได้
   ผลใหม่แต่ละครั้งอยู่ในโฟลเดอร์ UUID ภายใต้โฟลเดอร์ผลลัพธ์ที่ตั้งไว้ในโปรแกรม
7. ในแท็บ **ตรวจคู่รถ / ส่งออก OD** เลือกดูภาพต้นทางและปลายทาง
   กด **ยืนยันว่าเป็นคันเดียวกัน**, **คนละคัน** หรือ **รอตรวจใหม่**
   ผลตรวจบันทึกลงดิสก์ทันที เปิดต่อได้ด้วย **เปิดผลจับคู่เดิม**
8. แท็บ **เส้นทางที่ยืนยันแล้ว / OD** แสดง ID เส้นทาง จุดแรก จุดสุดท้าย
   ลำดับจุด และเวลา เมื่อยืนยัน A→B และ B→C ของรถเดียวกัน จะเชื่อมเป็น A→B→C
   และนับ OD A→C หนึ่งคัน การถอนผลยืนยันจะคำนวณเส้นทางใหม่
9. กดส่งออก CSV แล้วเลือกโฟลเดอร์ใหม่ เพื่อเก็บ `sightings.csv`, `pairs.csv`,
   `journeys.csv`, `od.csv` และ `provenance.json` เวลาส่งออกเป็น ISO 8601 ใน UTC
   หน้าจอแสดงเวลา UTC+07:00

## วิธีจับคู่และความหมายของคะแนน

เลือกภาพรถขนาดใหญ่ที่มี confidence สูงสุดไม่เกินสามภาพต่อ local track
และเฉลี่ย descriptor แบบถ่วงน้ำหนัก จากนั้นกรองคู่ด้วยเส้นทาง ทิศ เวลา และ class
แล้วใช้ cosine similarity ร่วมกับการจับคู่แบบ one-to-one ซึ่งยอมให้รถไม่มีคู่ได้
รถหนึ่งรายการมีรถก่อนหน้าและถัดไปอย่างละไม่เกินหนึ่งคัน ลำดับเวลาป้องกันวงจรย้อนเวลา
กรณีเลือกโหมด `shared_track` และเลือกจุดผ่านจาก run เดียวกัน ใช้ track ID เดียวกัน
เป็นเงื่อนไขแทนเกณฑ์ความคล้ายภาพ โหมดเริ่มต้น `independent` ใช้ภาพและเวลาสำหรับทุก run
ไม่มีการบังคับจับคู่ให้รถทุกคัน และไม่จับสอง local tracks ภายใน run เดียวกันในขั้นตอนนี้

คะแนน **ไม่ใช่ความน่าจะเป็นหรือความมั่นใจที่ผ่าน calibration**
เมื่อมีคู่ทางเลือกคะแนนใกล้กันตาม `ambiguity_margin` จะแสดง **กำกวม**
ทุกคู่เริ่มเป็น **รอตรวจ** แม้ระบบเสนอให้จับคู่แล้วก็ตาม
ตาราง OD นับเฉพาะคู่ที่มนุษย์ยืนยัน และปฏิเสธผลยืนยันที่ขัดกับข้อจำกัด one-to-one
ต้องถอนผลยืนยันเดิมก่อนเปลี่ยนไปเลือกอีกคู่

หากไม่ได้ระบุโมเดล ใช้ histogram สี HSV เป็น baseline เพื่อช่วยค้นหาคู่เท่านั้น
รถสี/รุ่นคล้ายกัน แสงต่างกัน มุมกล้องต่างกัน หรือรถถูกบัง อาจทำให้คะแนนผิดได้มาก
ภาพ crop อาจมีฉากหลัง และสามภาพอาจเป็นเฟรมติดกัน
ยังไม่ได้พิสูจน์ความแม่นยำ Re-ID กับรถจริงหรือการเปลี่ยนสภาพแสง
การยืนยันจากภาพที่แยกแยะไม่ได้ไม่สามารถทำให้ตัวตนแน่นอนขึ้นได้

## โมเดล Vehicle Re-ID แบบ ONNX (ถ้ามี)

เลือกโมเดล **vehicle appearance embedding** ที่ฝึกมาสำหรับ Re-ID โดยเฉพาะ
ไม่ใช่โมเดล YOLO detection/classification และไม่ดาวน์โหลดโมเดลให้อัตโนมัติ
รองรับ OpenCV DNN, input `float32 [1, 3, height, width]` แบบ RGB
หาร 255 แล้ว normalize ด้วย ImageNet mean `[0.485, 0.456, 0.406]`
และ std `[0.229, 0.224, 0.225]` output เป็น embedding เดียว `[1, D]`, D ≥ 16
เลือกขนาดภาพเข้าให้ตรงโมเดล (ค่าเริ่มต้นกว้าง 128 สูง 256)
ถ้า preprocessing หรือ output contract ของโมเดลต่างออกไป ต้อง export ให้เข้ากันก่อน
ระบบบันทึก SHA-256 ของโมเดลและ preprocessing ในผลลัพธ์

เลือก `reid_device: auto` เพื่อใช้ ONNX Runtime CUDA เมื่อพร้อม หรือ `0` / `cuda:0`
เพื่อบังคับ GPU 0 ต้องใช้ `tbs[onnx-gpu]` หรือ portable NVIDIA CUDA package
CPU ใช้ `reid_device: cpu` ตามเดิม ค่า `auto` ใช้ CPU ได้หาก GPU ไม่พร้อม
การบังคับ GPU จะรายงานข้อผิดพลาดเมื่อเริ่ม CUDA ไม่ได้ ไม่ตกไป CPU เงียบ ๆ
histogram สีไม่ได้ใช้ GPU ดู [WINDOWS_TEST.md](WINDOWS_TEST.md) สำหรับการติดตั้งและตรวจ driver

การรองรับ adapter ไม่ใช่หลักฐานว่าโมเดลใดผ่านความแม่นยำแล้ว
ควรวัด precision/recall ของคู่รถและความคลาดเคลื่อน OD จากคู่ที่กำกับ ID จริง
แยกตามจุด มุมกล้อง ช่วงกลางวัน/กลางคืน และความหนาแน่นรถ
ค่า threshold ต้องปรับตามโมเดล ไม่ใช้ค่าเดียวเป็นมาตรฐานทุกโมเดล
โมเดล detector ระหว่างจุดต้องใช้ความหมาย class ตรงกัน จึงจะผ่าน class gate

## CLI และค่าตั้งค่า

ดูตัวอย่าง [`configs/od.example.yaml`](../configs/od.example.yaml)
ซึ่งเป็นค่าจับคู่ **ผลวิเคราะห์ที่มีอยู่** แยกจาก project YAML สำหรับข้อกำหนดในอนาคต
บันทึก/เปิดค่าตั้งค่าผ่าน GUI ได้เช่นกัน Paths ในไฟล์ resolve จากตำแหน่งไฟล์ config

```bash
tbs reid run configs/od.example.yaml --output od-output
tbs reid review od-output/<uuid> --pair <pair-id> --decision accepted
tbs reid review od-output/<uuid> --pair <pair-id> --decision rejected
tbs reid export od-output/<uuid> --output reviewed-od-csv
```

`result.json` เก็บ sightings, embeddings, คู่เสนอ, สถานะการตรวจ และเส้นทางที่ยืนยัน
`manifest.json` ต้องมี `status: completed` ก่อนนำผลไปใช้
`pairs.csv` เก็บคะแนน เวลา สถานะและเวลาตรวจ สำหรับตรวจสอบย้อนหลัง
`journeys.csv` มี `journey_id`, origin, destination, ลำดับจุดและ sighting IDs
แต่ละ sighting อ้างกลับถึง source run และ local vehicle ID ได้
เส้นทางที่มีจุดซ้ำรองรับได้ถ้าพบในคนละ observation และเวลาเดินหน้า

จำกัด 100 observations, 5,000 local vehicles ต่อ observation, 10,000 sightings รวม
และ 200,000 candidate comparisons ต่อรัน หากเกินให้แบ่งช่วงสำรวจหรือบีบช่วงเวลาเดินทาง
ผลที่ยกเลิก/ล้มเหลวถูกระบุใน manifest และไม่เปิดเป็นผลสำเร็จ
ไม่แก้ไข source runs วิดีโอ หรือผลตรวจ YOLO
ยังไม่รวม OCR ป้ายทะเบียน, automatic clock sync/drift, การฝึกโมเดล,
การรันทุก site จาก project อัตโนมัติ, หรือการแก้ local tracker ID ที่แตกภายใน run

## วาดพื้นที่ประมวลผลและเลือกเฉพาะจุดในกล้องเดียวกัน

ในหน้าจุดสำรวจ เปิดแท็บ **พื้นที่ / จุดผ่าน** แล้ว:

1. กด **วาดกรอบพื้นที่ ROI** และคลิกมุมตรงข้ามสองมุมบนภาพ ใช้ล้อเมาส์ซูมได้
   กรอบบันทึกเป็นพิกเซลของวิดีโอต้นฉบับ ไม่ใช่พิกเซลบนจอ ภาพจะพักเมื่อเริ่มวาด
   กด Esc ยกเลิก หรือ **ใช้ทั้งภาพ** เพื่อล้าง ROI
2. ตั้งชื่อจุด เช่น A เลือกทิศ และกด **วาดเส้นผ่านจุด 2 คลิก**
   คลิกปลาย p1 แล้ว p2 จากนั้นเพิ่ม B หรือจุดอื่น ๆ ด้วยวิธีเดียวกัน
   เลือกชื่อจุดเดิมแล้ววาดใหม่เพื่อแก้ตำแหน่ง หรือลบจุดที่ไม่ใช้
3. บันทึก site และประมวลผลใหม่ จุดผ่านจะถูกบันทึกใน `point_passages.parquet`
   พร้อม local vehicle ID, เวลา, ทิศ, passage ID และเฟรมที่ตรวจพบ
4. ในหน้าผลลัพธ์ เลือก **เลือกเฉพาะรถที่ผ่านจุด** เป็น A
   ตารางรถ/trajectory, ภาพ overlay, การนับ และ CSV จะคัดเฉพาะรถที่ผ่าน A
   ตาราง `point_passages` แสดงเหตุการณ์ของ A เท่านั้น
   การเลือกนี้แสดงประวัติที่เก็บไว้ทั้งหมดของรถที่ผ่าน A ไม่ใช่ตัด trajectory ให้เหลือเฉพาะบริเวณ A
   เลือก **รถทุกคัน** เพื่อกลับไปดูผลทั้งหมด CSV มี `selection.json` ระบุจุดที่ใช้กรอง
5. ในหน้า **จับคู่รถ / OD** เพิ่มโฟลเดอร์ผล run เดียวกันสองครั้ง
   ช่อง **เฉพาะจุดผ่านในผล** เลือก A ในรายการแรกและ B ในรายการที่สอง
   ระบบเลือกจุดที่ยังไม่ได้ใช้ให้เบื้องต้น และใช้ชื่อจุดเป็นจุดสังเกต
   แก้ชื่อจุดสังเกตได้ตามตำแหน่งจริง จากนั้นเพิ่มเส้นทาง A→B พร้อมช่วงเวลาเดินทาง
6. กดจับคู่ จะเสนอเฉพาะรถที่ผ่านทั้งสองจุดตามทิศและเวลา
   ค่าเริ่มต้นใช้ภาพและเวลาเสนอคู่ได้แม้ track ID ต่างกัน หากมีการติดตามต่อเนื่องแน่นอน
   สามารถเลือกโหมด `shared_track` เพื่อใช้ **track ID เดียวกัน** เป็นหลัก
   และแสดง **ID เดียวกัน** ในตารางคู่รถ
   เวลาผ่าน A/B เป็นเวลาที่จุดกึ่งกลางล่างของกรอบรถข้ามเส้น โดย interpolate ระหว่างเฟรมจริง
   ตรวจยืนยันแล้วส่งออก OD ได้เหมือนขั้นตอนข้ามกล้อง

ROI คัด detection เมื่อ **จุดกึ่งกลางล่างของกรอบรถอยู่ภายในหรือบนขอบ ROI**
จุดผ่านต้องข้ามส่วนของเส้น p1→p2 จริง ไม่ใช่เพียงเข้าใกล้หรือข้ามส่วนต่อของเส้นนอกปลาย
ทิศบวกคือนิพจน์ `(p2.x-p1.x)*(y-p1.y) - (p2.y-p1.y)*(x-p1.x)` เปลี่ยนจากลบเป็นบวก
เลือกทั้งสองทิศเมื่อต้องการนับการผ่านทุกทิศ การกลับมาผ่านซ้ำจะมี passage ID ใหม่

กรอบ ROI ต้องครอบคลุมเส้นทางระหว่างจุดที่ต้องการรักษา ID ต่อเนื่อง
ถ้ารถหายเกิน `track_max_gap_s` หรือออกจาก ROI แล้วกลับเข้ามาจนได้ track ID ใหม่
โหมด `independent` จะใช้ภาพและเวลาเสนอ Candidate ระหว่าง ID ที่แตกเพื่อให้คนยืนยัน
โดยไม่ได้เชื่อม track ภายใน source run หรือแก้ไข ID ต้นฉบับให้โดยอัตโนมัติ
กรอบ ROI/จุดผ่านใช้ร่วมกับคลิปใน site เดียวกัน จึงต้องเป็นมุมกล้องและขนาดภาพเดียวกัน
ระบบปฏิเสธพิกัดที่อยู่นอกขนาดภาพ แทนการปรับขนาดกรอบให้อัตโนมัติ

การวาดกรอบไม่ต้องใช้ calibration แต่การประมวลผลจุดสำรวจยังต้องมี calibration
ส่วนหน้า **ทดสอบวิดีโอ** วาด ROI เพื่อคัด detection ได้โดยไม่ต้องมี calibration
และยังไม่สร้าง track/เวลาผ่านจุดในโหมดนั้น
ROI เป็นการคัดผลหลัง detector จึงไม่อ้างว่าทำให้ YOLO inference เร็วขึ้น

ตัวอย่างส่วนเพิ่มเติมใน site YAML (หน่วยพิกเซล):

```yaml
image_regions:
  roi: [[0, 0], [320, 0], [320, 120], [0, 120]]
  points:
    - id: A
      p1: [80, 20]
      p2: [80, 110]
      direction: 0
    - id: B
      p1: [180, 20]
      p2: [180, 110]
      direction: 0
```

ตัวอย่างค่าจับคู่สองจุดจาก run เดียวกัน:

```yaml
schema_version: 1
observations:
  - id: entry
    point_id: A
    run: ../output/the-same-run
    passage_point: A
  - id: exit
    point_id: B
    run: ../output/the-same-run
    passage_point: B
links:
  - from: A
    to: B
    min_travel_s: 0.1
    max_travel_s: 60
```

แต่ละรายการใน run เดียวกันต้องเลือก `passage_point` ต่างกัน และใช้ค่าชดเชยนาฬิกาเดียวกัน
กรณีนี้ใช้เวลาผ่านเส้น ไม่ใช้เวลาปรากฏครั้งแรก/สุดท้ายตลอดทั้ง run
ผลวิเคราะห์เก่าที่ไม่มีจุดผ่านต้องประมวลผลใหม่หลังวาดจุด จึงจะเลือกจุดในผลได้
