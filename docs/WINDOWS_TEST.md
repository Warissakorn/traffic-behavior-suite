# ทดสอบ GUI บน Windows

## จากซอร์ส (รองรับวิดีโอจริงเมื่อเพิ่ม detection dependencies)

1. ดาวน์โหลด ZIP ของ branch ที่ต้องการทดสอบและแตกไฟล์
2. ติดตั้ง Python **3.12 x64** แล้วดับเบิลคลิก `Setup-Windows.cmd` (ใช้อินเทอร์เน็ตครั้งแรก)
3. เปิด `Launch-TBS.cmd` → แท็บ **ตัวอย่าง / ล่าสุด** → **ทดสอบตัวอย่าง**
4. ผลที่ต้องได้: 50 frames, 1 track, 1 crossing; เปิดหน้าผลลัพธ์และตรวจภาพได้
5. `Test-Windows.cmd` ตรวจ environment, benchmark และ GUI/worker smoke อัตโนมัติ

## ทดสอบวิดีโอจริงโดยไม่ใช้ calibration

1. กด **เปิดวิดีโอ** หรือเลือกไฟล์ในหน้า **ทดสอบวิดีโอ → วิดีโอจริง**
2. ดูภาพ เล่น/พัก กลับต้นคลิป หรือเลื่อนเวลาได้ทันที ไม่ต้องมี site YAML หรือโมเดล
3. หากจะลอง detection ให้รัน `Setup-Detection-Windows.cmd` เพิ่ม แล้วเลือก local YOLO
   weights ตั้ง Confidence, Device และ Class IDs (ปล่อยว่างเพื่อใช้ทุก class ของโมเดล)
4. เลือกโฟลเดอร์ผลลัพธ์ แล้วกด **ทดสอบ detection ทั้งคลิป**
5. หน้าประมวลผลแสดงจำนวนเฟรม/detections และยกเลิกได้ เมื่อสำเร็จเปิดหน้าภาพ + overlay
   เพื่อดูกรอบ class/confidence พร้อมเลื่อน/เล่นผลตาม PTS
6. **ส่งออก CSV** ได้ `detections.csv` (กรอบหน่วย px), `frames.csv`, `counts.csv`
   และ manifest; counts เป็นจำนวน detection ต่อ class รวมทุกเฟรม ไม่ใช่จำนวนรถไม่ซ้ำ

โหมดนี้เก็บพิกัดภาพเท่านั้น (`gx`, `gy`, `ground_method`, `track_id` เป็น null)
ไฟล์ vehicles/trajectories/line_crossings เป็นตารางว่างตาม schema เพื่อให้เปิดผลได้ด้วย
ResultStore เดิม; manifest ระบุ `run_mode: video_test` ส่วน epoch คือเวลาเริ่มงาน UTC
เวลาในคลิปเริ่มที่ PTS แรก ไม่ใช่เวลาถ่ายจริง inference ไม่ดาวน์โหลด weights เอง; ใช้ปุ่มดาวน์โหลด/อัปเดตโมเดลเมื่อจำเป็น
หากอ่านระยะเวลาท้ายคลิปไม่ได้ จะยังเล่นต่อเนื่องได้ แต่ slider เวลาไม่เปิดใช้งาน

### เลือกตัดภาพตาม ROI ก่อนตรวจจับ

วาด **กรอบพื้นที่ ROI** บนภาพ แล้วเปิด **ตัดภาพตาม ROI ก่อนส่งเข้า YOLO**
ในหน้า **ทดสอบวิดีโอ** หรือ **จุดสำรวจ → พื้นที่ / จุดผ่าน**
เมื่อเปิด โปรแกรมส่งเฉพาะภาพภายในกรอบเข้า detector เมื่อปิด จะตรวจทั้งภาพแล้วคัดเฉพาะรถใน ROI เช่นเดิม
กด **ใช้ทั้งภาพ** เพื่อล้าง ROI และปิดการตัดภาพ

ทั้งสองแบบใช้วิดีโอต้นฉบับเต็มภาพในหน้าผลลัพธ์ กรอบรถ, ROI, เส้นผ่านจุด และ CSV ใช้พิกัดภาพเต็ม
โปรแกรมบวกตำแหน่งมุมซ้ายบนของภาพที่ตัดกลับเข้ากรอบรถก่อน tracking, calibration และ Re-ID
ปุ่ม **ตรวจและลองโมเดล** ใช้ตัวเลือก ROI เดียวกันและแสดงกรอบบนภาพเต็มด้วย
ตัวเลือกบันทึกใน site YAML ที่ `image_regions.crop_before_detect` (ค่าเริ่มต้น `false`)
ผลลัพธ์บันทึกขนาดภาพที่ส่งเข้า detector และตำแหน่ง crop ใน `manifest.json` ส่วน `inference_region`

ควรเผื่อขอบให้เห็นรถเต็มคัน การตัดชิดตัวรถอาจลดความแม่นยำของกรอบและภาพสำหรับจับคู่
ความเร็วไม่ได้เพิ่มตามสัดส่วนพื้นที่เสมอไป เพราะยังขึ้นกับ Image size และ backend ของโมเดล
ลองลด Image size ให้เหมาะสมและเปรียบเทียบความเร็ว/ความแม่นยำบนวิดีโอเดียวกัน

## วิเคราะห์จุดสำรวจด้วย calibration

### นำเข้าชุดคลิปทั้งวัน

ใน **จุดสำรวจ → วิดีโอ → นำเข้าชุดคลิป…** เลือกหลายไฟล์หรือทั้งโฟลเดอร์
เลือกแหล่งเวลา แล้วตรวจตารางก่อนเพิ่มเข้าจุดสำรวจ:

- **วัน–เวลาจากชื่อไฟล์** อ่านรูปแบบเช่น `CAM_20261020_060000.mkv` หรือ `2026-10-20_06-00-00.mp4`
  โดยใช้ timezone จากช่องเวลาอ้างอิง เช่น `+07:00` หากชื่อไฟล์ต่างรูปแบบ กรอก format เช่น `CAM_%Y%m%d_%H%M%S`
  แบบไม่รวมนามสกุล ชื่อที่มีหลาย timestamp จะไม่เดาให้เลือกเอง
- **เวลาเริ่ม + ช่วงห่างที่กำหนด** เช่น เริ่ม `2026-10-20T06:00:00+07:00` ห่างกัน 10 นาที
  เป็นข้อสมมุติที่ต้องตรวจทาน ไม่สามารถรู้คลิปขาดจากชื่อที่ไม่มีเวลาได้แน่นอน
- แสดงเวลาเริ่ม–ปลาย ช่องว่าง เวลาซ้อน ขนาดภาพ และไฟล์เนื้อหาเหมือนกัน
  ตรวจเนื้อหาเฉพาะกลุ่มไฟล์ขนาดเท่ากัน; ไฟล์เหมือนกันเป็นคำเตือน เพราะช่วงภาพนิ่งอาจเหมือนกันจริง
  ไม่ใช้เวลาแก้ไขไฟล์บนดิสก์แทนเวลาถ่ายโดยอัตโนมัติ
- เอาเครื่องหมายเลือกคลิปออกได้โดยเวลาเริ่มคลิปอื่นไม่ขยับ คลิปหายยังเป็นช่องว่าง
  เวลาซ้อนต้องแก้ก่อนนำเข้า ส่วนคำเตือนต้องตรวจทานและติ๊กยอมรับก่อนเพิ่มรายการ
- เลือกแทน playlist เดิม หรือเพิ่มต่อได้ โปรแกรมปฏิเสธการเพิ่ม path เดิมซ้ำ
  บันทึก site เพื่อเก็บเวลาและที่มาของเวลา ถ้าแก้เวลาในตารางภายหลัง ที่มาจะเป็น `manual`

หากอ่านระยะเวลาคลิปได้ไม่แน่นอน ปลายคลิปอ้างอิง PTS เฟรมท้ายและแสดงคำเตือน
ช่องว่างเกิน 0.25 วินาทีจะแสดงในหน้าตรวจคลิป ไม่ปรับเวลาเพื่อปิดช่องว่างให้เอง

### พักงานและทำงานต่อ

ระหว่าง **ประมวลผลจุดสำรวจ** กด **พักงาน / บันทึกจุดทำต่อ** ได้
โปรแกรมเก็บข้อมูลตรวจจับและสถานะติดตามไว้ใน SQLite เมื่อจบแต่ละคลิป
หากพักหรือโปรเซสหยุดกลางคลิป คลิปนั้นจะเริ่มใหม่ ส่วนคลิปที่ commit แล้วไม่รัน YOLO ซ้ำ
หน้าประมวลผลแสดงจำนวนคลิปที่บันทึกแล้วและสถานะรายคลิป

เปิด **ประมวลผล → งานที่พักไว้ / ทำต่อ…** เพื่อเลือกงานเดิม แม้ปิดโปรแกรมแล้วเปิดใหม่
เลือกโฟลเดอร์ผลลัพธ์อื่น หรือเลือกโฟลเดอร์ run โดยตรงได้ ใช้ค่าตั้งค่าที่บันทึกไว้ในงานนั้น
โปรแกรมตรวจ SHA-256 ของต้นฉบับ โมเดล calibration และรุ่น engine ก่อนทำต่อ
ขั้นตรวจไฟล์จะอ่านข้อมูลจากดิสก์ แต่ไม่ใช่การตรวจจับรถใหม่
หากแก้เวลา/ROI/โมเดล หรือเปลี่ยนไฟล์ ต้องเริ่มงานใหม่แทนการนำผลคนละรุ่นมาปนกัน

เก็บ `source.yaml`, `journal.sqlite` และไฟล์ประกอบในโฟลเดอร์ run ไว้ด้วยกัน
SQLite ต้องใช้พื้นที่ดิสก์เพิ่มเติมสำหรับข้อมูลดิบและ transaction ผล Parquet สร้างจากข้อมูลที่บันทึกแล้วเมื่อจบงาน
หากหยุดระหว่างสร้างผล จะทำขั้นสร้างผลใหม่จาก journal โดยไม่ตรวจคลิปที่บันทึกแล้วซ้ำ
ผลที่ยังไม่สำเร็จเปิดเป็นรายงานสำเร็จไม่ได้ ระบบนี้ใช้กับงาน site/demo
โหมดทดสอบ detector คลิปเดียวมีปุ่มยกเลิกตามเดิมและยังไม่รองรับพัก/ทำต่อ

CLI: `tbs resume path/to/run` ทำต่อจาก `source.yaml` ในงานนั้น
worker รองรับ `--pause-after-clips N` สำหรับพักอัตโนมัติเมื่อ commit ครบ N คลิป

กด **ใช้วิดีโอนี้ตั้งค่าจุดสำรวจ** หรือเปิด/สร้าง site แล้วเลือกเวลาเริ่มจริง,
Camera YAML แบบ planar_homography (สร้างจากภาพในแท็บ **กล้อง** ได้) และ local weights กดตรวจความพร้อมก่อนรัน
เพื่อคำนวณ trajectory ความเร็ว และเส้นนับ; input image ต้องผ่าน undistort แล้ว
ดูภาพได้แม้ยังไม่ได้เลือก calibration แต่การวาดเส้นบนพิกัดเมตรต้องโหลด calibration ก่อน

ฟอร์มรองรับ playlist, timezone, camera import, เส้นนับบนภาพและการแก้พิกัดเมตร,
model path, ช่อง Confidence/Device/Class IDs และ tracking options JSON ตาม Foundation schema
การเพิ่มหลายคลิปจะจัดเวลาเริ่มต่อเนื่องจากระยะเวลา PTS ของแต่ละคลิป
ต้องแก้เวลาให้ตรงการถ่ายจริง โดยเฉพาะคลิปที่มีช่วงว่างหรืออ่านระยะเวลาไม่ได้
ตรวจความพร้อมอ่านเฟรมแรก/ท้ายและตรวจเวลาซ้อนในงานเบื้องหลัง; pipeline ยังคงตรวจ PTS ทุกเฟรม
เลือกเส้น → วาดสองจุด; zoom ด้วยล้อเมาส์; ลาก endpoint ของเส้นที่เลือกเพื่อแก้ตำแหน่ง

ผลลัพธ์มีตารางการนับ, รายคัน/trajectory แบบแบ่งหน้า, วิดีโอ overlay ที่ seek ตาม PTS
และ CSV UTF-8 BOM พร้อมหน่วย/epoch/site/run ID
ค่าที่ pipeline ยังไม่คำนวณแสดงเป็น missing; ผลจำลองไม่ได้ยืนยันความแม่นยำกล้องจริง

แผงตั้งค่าปรับสัดส่วนหรือพับด้วย **แผงตั้งค่า** ได้ และซ่อน navigation ด้วย **เมนู**
ภาพและตารางยืดตามพื้นที่หน้าต่าง ฟอร์มที่ยาวเลื่อนภายในแผง ปุ่มรันอยู่ด้านล่างเสมอ
โปรแกรมจำขนาดหน้าต่างและสัดส่วนแผงเมื่อปิด
ล้อเมาส์เหนือช่องตัวเลข รายการเลือก หรือแถบเวลา จะไม่เปลี่ยนค่าแม้ช่องนั้นมีโฟกัส
ในฟอร์มที่เลื่อนได้ ล้อจะเลื่อนฟอร์มแทน ใช้การพิมพ์ คลิก หรือปุ่มลูกศรเพื่อเปลี่ยนค่าโดยตั้งใจ
ล้อเมาส์เหนือภาพวิดีโอ / ภาพปรับเทียบยังใช้ซูมภาพได้ และรายการที่เปิดอยู่ยังเลื่อนดูได้

### สร้าง Camera YAML ในโปรแกรม

1. เปิดวิดีโอ → **ใช้วิดีโอนี้ตั้งค่าจุดสำรวจ** หรือเลือกวิดีโอในหน้า **จุดสำรวจ**
2. เลื่อนวิดีโอไปยังเฟรมที่เห็นพื้นถนนชัด แล้วเปิดแท็บ **กล้อง → สร้าง Camera YAML จากภาพ…**
   โปรแกรมใช้เฟรมปัจจุบัน หรือกด **เปิดภาพอ้างอิง…** เพื่อใช้ภาพจากกล้องเดียวกัน
3. เลือกวิธีใดวิธีหนึ่ง:
   - **ระยะตามแนวถนน: ต้นช่วง → ปลายช่วง** (ค่าเริ่มต้น): ใช้กับช่วงถนนตรงที่อยู่บนระนาบเดียว
     คลิก P1 ต้นช่วง → P2 ปลายช่วง บนขอบเดียวกัน แล้ว P3 ปลายช่วง → P4 ต้นช่วง บนอีกขอบหนึ่ง
     กรอกระยะตามแนวรถวิ่ง P1→P2 และความกว้างตั้งฉากขวางถนน P1→P4 ที่วัดจริงเป็นเมตร
     คู่ต้นช่วง / ปลายช่วงต้องอยู่ที่หน้าตัดเดียวกันทั้งสองขอบ โปรแกรมแสดงกรอบอ้างอิงและแนวระยะบนภาพ
     แกน X เป็นแนวขวางถนน แกน Y เป็นแนวตามถนน ไม่ต้องเป็นเส้นตั้งหรือแนวนอนบนหน้าจอ
   - **สี่เหลี่ยมที่ทราบกว้าง × ยาว**: วัดพื้นที่สี่เหลี่ยมจริงบนพื้นถนน กรอกกว้าง/ยาวเป็นเมตร
     แล้วคลิกมุมเรียงรอบขอบ P1 → P2 → P3 → P4 โดย P1→P2 คือด้านกว้าง และ P2→P3 คือด้านยาว
     มุมทั้งสี่ไม่จำเป็นต้องดูเป็นสี่เหลี่ยมมุมฉากในภาพ เพราะมี perspective
   - **พิกัดพื้นอิสระ**: คลิกอย่างน้อย 4 จุด แล้วกรอกพิกัด X,Y ที่วัดจริงเป็นเมตรในแต่ละแถว
     ใช้จุดกำเนิดและแกนเดียวกันทุกจุด แนะนำ 6 จุดขึ้นไปกระจายทั่วบริเวณที่ต้องการวัด
4. ซูมด้วยล้อเมาส์ ปิด **คลิกเลือกจุด** เพื่อลากภาพได้ เลือกแถวแล้วกด **ย้ายจุดที่เลือก**
   เพื่อคลิกแก้ตำแหน่ง หรือแก้พิกัดพิกเซลในตาราง
5. กด **คำนวณและตรวจจุดอ้างอิง** ดู RMSE/ค่าสูงสุดหน่วยเมตรและความคลาดเคลื่อนย้อนกลับหน่วยพิกเซล
6. กด **บันทึก Camera YAML และใช้** เลือกตำแหน่งไฟล์ โปรแกรมเลือกไฟล์ให้ทันที
   แล้วกด **บันทึก site** เพื่อเก็บการอ้างอิงไฟล์กล้องไว้ด้วย

ไฟล์ที่สร้างมี `projection: planar_homography`, เมทริกซ์ `image_to_ground`, ขนาดภาพต้นฉบับ
และคู่จุดที่ใช้คำนวณ ไม่ต้องกรอกเมทริกซ์เอง โปรแกรมไม่ยอมบันทึกเมื่อจุดไม่ครบ จุดซ้ำ
อยู่บนเส้นตรง หรือพิกัดใช้คำนวณไม่ได้ การแก้ค่าจะคำนวณใหม่ตอนบันทึกเสมอ

ต้องวัดระยะจากสถานที่จริงหรือแผนสำรวจที่เชื่อถือได้ โปรแกรมไม่ทราบจำนวนเมตรจากภาพเพียงอย่างเดียว
4 จุดอาจได้ RMSE ใกล้ศูนย์แม้กรอกระยะผิด ควรตรวจด้วยจุด/ระยะอีกชุดหนึ่งที่ไม่ได้ใช้คำนวณ
วิธีนี้ใช้กับพื้นระนาบเดียว ภาพที่แก้ lens distortion แล้ว และมุมกล้อง/ความละเอียดเดียวกัน
เมื่อกล้องขยับ เปลี่ยนซูม ครอป หรือเปลี่ยนความละเอียด ต้องทำ calibration ใหม่
Camera YAML ที่สร้างในโปรแกรมระบุขนาดภาพ หากขนาดไม่ตรงกับวิดีโอ โปรแกรมจะแจ้งและไม่ใช้คำนวณพิกัดพื้น
หากเปลี่ยนจุดกำเนิดหรือแกนของพื้น ให้ตรวจตำแหน่งเส้นนับเดิมด้วย
การตรวจจับ ROI/จุดผ่านแบบพิกเซลและการจับคู่จากภาพไม่ต้องใช้ Camera YAML

### ระยะตามถนนกับความแม่นยำของความเร็ว

ใช้ระยะที่วัดบนผิวถนนตามทางรถวิ่ง และวางจุดอ้างอิงครอบคลุมช่วงใกล้–ไกลที่จะวัดความเร็ว
การปรับเทียบยังคำนวณ homography จากพื้นที่ 4 จุด ไม่ใช้ระยะ 2 จุดเป็นสเกลพิกเซลต่อเมตรคงที่ทั้งภาพ
เพราะ perspective ทำให้ระยะบนภาพของช่วงใกล้กล้องกับไกลกล้องต่างกัน
หนึ่งระยะตามแนวถนนเพียงอย่างเดียวไม่เพียงพอที่จะหาเมทริกซ์แปลงพิกัดพื้น 2 มิติ
จึงต้องวัดความกว้างตั้งฉากด้วย หรือใช้โหมดพิกัดพื้นอิสระที่มีจุดสำรวจอย่างน้อย 4 จุด

วิธีตามแนวถนนเหมาะกับงานนี้ แต่ไม่ได้รับประกันว่าแม่นยำที่สุดโดยอัตโนมัติ
ควรตรวจด้วยระยะตามถนนอีกช่วงหนึ่งที่ไม่ได้ใช้คำนวณ และตรวจหลายตำแหน่ง / ช่องจราจร
ค่าความเร็วใช้ระยะบนพื้น 2 มิติจากตำแหน่งรถตามเวลา PTS จริง จึงยังรวมการเคลื่อนขวางถนนเมื่อเปลี่ยนเลน
ความแม่นยำยังขึ้นกับระยะสำรวจ, lens distortion, timestamp และจุดกึ่งกลางล่างของกรอบรถ
ซึ่งอาจคลาดจากจุดสัมผัสถนนจริงเมื่อรถบังกันหรือเห็นต่างมุม
ถนนโค้งไม่ควรใส่ระยะตามโค้งแทนด้านตรงของกรอบ และถนนที่เปลี่ยนความลาดชันต้องใช้การปรับเทียบเป็นช่วง
หรือแบบจำลองผิวถนนเพิ่มเติม ไม่สามารถแทนด้วย homography ระนาบเดียวได้ถูกต้องทุกจุด

## Portable test build: CPU และ NVIDIA CUDA

Workflow **Windows portable test** สร้างโปรแกรม Windows x64 สองรุ่น:

| Artifact | การใช้งาน |
|---|---|
| `TBS-Windows-cpu` | เปิดวิดีโอ ตรวจ YOLO จับคู่รถและ OD บน CPU |
| `TBS-Windows-cuda` | ความสามารถเดียวกัน พร้อม PyTorch CUDA 12.8 และ ONNX Runtime GPU สำหรับ NVIDIA |

1. เปิด GitHub repository → **Actions → Windows portable test** → เลือก run ที่สำเร็จ
2. ดาวน์โหลด Artifact รุ่นที่ต้องการ (เก็บ 7 วัน) ถ้าเป็นการรันเอง เลือก **Run workflow**
   และ profile `cpu`, `cuda` หรือ `both` ได้หลัง workflow อยู่ใน repository
3. แตก ZIP ของ artifact แล้วแตก `TBS-Windows-cpu.zip` หรือ `TBS-Windows-cuda.zip` ภายในอีกครั้ง
4. เปิด `TBS/TBS.exe` ไม่ต้องติดตั้ง Python; ต้องเก็บ `TBSWorker.exe` และ `_internal` ไว้ด้วยกัน
5. เลือก/ดาวน์โหลด weights ผ่านโปรแกรม แล้วทดสอบวิดีโอจริง โมเดล pretrained ไม่ได้รวมใน ZIP

รุ่น CUDA มีขนาดใหญ่กว่ารุ่น CPU มากเพราะรวม GPU runtime
ต้องมี NVIDIA GPU และ driver ที่รองรับ CUDA 12.8 แนะนำอัปเดต driver จาก NVIDIA
ไม่ต้องติดตั้ง CUDA Toolkit เพื่อใช้แพ็กเกจนี้ ส่วน AMD/Intel ยังไม่รองรับผ่าน CUDA
ไฟล์ `.zip.sha256` ใช้ตรวจ SHA-256 ของ ZIP ได้ และ `build-info.json` ระบุ commit กับ package versions

### เลือก GPU ในโปรแกรม

- YOLO: Device `auto` เลือก CUDA GPU 0 ถ้าพร้อม ไม่เช่นนั้นใช้ CPU
- Device `0` / `cuda:0` บังคับ NVIDIA GPU; ถ้าไม่พร้อมจะแจ้งข้อผิดพลาด ไม่อ้างว่าประมวลผลด้วย GPU
- ปุ่ม **ตรวจ GPU ที่พร้อมใช้** แสดงชื่อ GPU; เปิด **FP16** ได้เฉพาะ YOLO บน CUDA
- Re-ID ONNX: เลือก **อุปกรณ์ Re-ID ONNX** เป็น `auto` หรือ `0` ในหน้าจับคู่รถ
  ต้องเลือกโมเดล Vehicle Re-ID ONNX ด้วย histogram สีทำงานบน CPU
- manifest ของ YOLO และผล Re-ID บันทึก backend/device ที่เลือกใช้จริง
  งาน decode วิดีโอ, tracking, geometry, CSV/Parquet และ candidate assignment ยังใช้ CPU
  FP16 ไม่ได้เปลี่ยน ONNX input contract ซึ่งยังเป็น float32 RGB

`Test-GPU.cmd` ในโฟลเดอร์โปรแกรมทดสอบ inference จริงบน GPU 0 ด้วยโมเดลสุ่มในเครื่อง
ทั้ง YOLO11/YOLO26 และ ONNX embedding เล็ก ๆ ดูผลที่ `gpu-test.json` และ `gpu-test.log`
การทดสอบนี้ยืนยัน runtime/driver ไม่ได้วัดความแม่นยำโมเดล
รุ่น CPU จะไม่ผ่านการทดสอบ GPU ซึ่งเป็นพฤติกรรมที่ถูกต้อง

### สิ่งที่ GitHub Actions ตรวจ

รัน source tests จากนั้นใช้ PyInstaller สร้าง GUI/worker ที่แชร์ runtime folder เดียว
และรัน frozen YOLO11/YOLO26, ONNX Re-ID บน CPU และ GUI → worker demo smoke ก่อนสร้าง ZIP
CUDA job ตรวจว่า wheel/runtime เป็น CUDA 12.8 และมี CUDA provider
ทดสอบ worker ที่แพ็กแล้วโดยพักหลังคลิปแรก ทำต่อ และเปรียบเทียบทุกตารางกับการรันรวดเดียวด้วย
Windows hosted runner ไม่มี NVIDIA GPU จึงยังไม่ใช่หลักฐานว่า CUDA inference ผ่านบนการ์ดจริง
ให้รัน `Test-GPU.cmd` บนเครื่องทดสอบด้วย
ถ้า tests, packaging, smoke หรือ artifact upload ล้มเหลว workflow จะแสดง failure
และพยายามแนบ build diagnostics; ไม่แสดง success ทั้งที่ไม่มีไฟล์ให้ดาวน์โหลด

สร้างเองบน Windows จากซอร์ส:

```powershell
py -3.12 -m venv .venv-build
.venv-build\Scripts\python.exe tools/windows/install_profile.py --profile cpu --build
.venv-build\Scripts\python.exe tools/windows/build.py --profile cpu
# เลือก --profile cuda ในทั้งสองคำสั่งหากต้องการแพ็กเกจ NVIDIA
```

ไฟล์อยู่ที่ `dist/TBS-Windows-cpu.zip` หรือ `dist/TBS-Windows-cuda.zip`
การสร้าง `.exe` ต้องใช้ Windows; Linux cloud ใช้ตรวจ source/runtime และ workflow ได้

### ติดตั้งจาก source บนเครื่อง NVIDIA

รัน `Setup-GPU-Windows.cmd` แล้วเปิด `Launch-TBS.cmd`
ติดตั้ง PyTorch 2.7.1 / torchvision 0.22.1 จาก official CUDA 12.8 index พร้อม ONNX Runtime GPU
`Setup-Detection-Windows.cmd` ใช้ runtime CPU ที่ pin ไว้แทน
อย่าติดตั้ง `onnxruntime` และ `onnxruntime-gpu` ซ้อนกันใน environment เดียว
setup scripts จะถอน distribution ฝั่งตรงข้ามก่อนติดตั้ง profile ใหม่

## เมื่อพบปัญหา

environment รุ่นเดิมใน LOCALAPPDATA สามารถคัดลอกเข้าโปรเจกต์โดยรัน
`py -3.12 tools/windows/migrate_environment.py` เมื่อยังไม่มี `.venv`
เครื่องมือนี้คัดลอก dependencies และปรับ launcher โดยเก็บต้นฉบับไว้ ไม่ดาวน์โหลดแพ็กเกจใหม่
ยังต้องติดตั้ง Python 3.12 x64; `.venv` ไม่ใช่ portable build และเมื่อย้ายโปรเจกต์ต้องรัน Setup ใหม่

* เปิด `Launch-TBS-Debug.cmd` เพื่อเห็น traceback และข้อความ dependency
* environment และ dependencies อยู่ใน `.venv` ภายในโฟลเดอร์โปรเจกต์ (ไม่รวมใน Git)
* log/settings อยู่ใน `%LOCALAPPDATA%/TrafficBehaviorSuite`
* portable GUI เปิดไม่ขึ้น: ดู `logs/frozen-startup.log`; CI เก็บ `startup-smoke.log` และแสดง traceback ใน Checks
* log งานอยู่ใน `sessions/<session>.log`; launcher log อยู่ใน `logs/startup.log`
* ยกเลิกปกติรอเฟรม/stage ปัจจุบันคืน control; หลัง 5 วินาทีเลือก force-stop ได้
* failed/cancelled/interrupted run เป็นผลบางส่วน ไม่เปิดเป็นผลวิเคราะห์สำเร็จ
* artifact quota เต็ม: workflow จะแจ้ง upload failure ต้องคืนพื้นที่ Artifact แล้วรันใหม่
* setup ถูกขัดจังหวะ: รัน Setup ใหม่; ย้ายโฟลเดอร์ซอร์สให้ setup environment สำหรับ path ใหม่

CI ตรวจ Python tests บน Windows/Linux, GUI offscreen และ Windows frozen build;
การแสดงผล DPI, hardware decoder/driver และความแม่นยำภาคสนามยังต้องตรวจบนเครื่องจริง
