# แผนปรับปรุงงานสำรวจรถเข้า–ออกตลอดวัน

สถานะ: ชุดแรก (นำเข้าคลิปและ checkpoint) ลงมือทำแล้ว ส่วนชุดที่สอง–สามยังเป็นงานถัดไป

การจัดเก็บชุดแรกใช้ตาราง SQLite แบบมีชนิดข้อมูลเป็นแหล่งข้อมูลหลัก
และ commit ข้อมูลกับสถานะติดตามพร้อมกันรายคลิป แทนการแยกชิ้น Parquet ระหว่างประมวลผล
เมื่อครบชุดจึงสร้าง Parquet ที่ ResultStore เดิมอ่านได้ หากหยุดขั้นสร้างผลสามารถสร้างใหม่จาก journal
โดยไม่ตรวจจับคลิปที่ commit แล้วซ้ำ จึงไม่ต้อง append Parquet ที่เขียนไม่ครบหลัง crash

เป้าหมายคือวิเคราะห์วิดีโอช่วง 06:00–22:00 ประมาณ 96 คลิป คลิปละ 10 นาที
จากกล้องที่เห็นรถเข้าโครงการชัดเจน แต่จุดสังเกตหลังทางออกมีรถจากซอยปะปน
เสนอคู่จากภาพและเวลาให้คนยืนยัน รองรับไม่มีป้ายทะเบียน ภาพต่างมุม และรถกลับมาหลายรอบ
จำนวน 96 คลิปเป็นกรณีใช้งานเป้าหมาย ไม่ใช่ข้อจำกัดจำนวนไฟล์ของระบบ

## ข้อเท็จจริงจากโค้ดปัจจุบัน

- มี playlist, เวลา PTS, การตรวจเวลาซ้อน, GPU, ROI crop และพิกัดผลลัพธ์ภาพเต็มแล้ว
- `gui/main_window.py:add_videos` จัดเวลาเริ่มโดยนำความยาวคลิปก่อนหน้ามาบวกต่อกัน
  ไม่ใช่การอ่านเวลาถ่ายจริงจากชื่อไฟล์ และอาจทำให้ช่วงที่คลิปหายถูกจัดต่อกันโดยไม่ตั้งใจ
- `pipeline.py` เขียน Parquet ต่อเนื่องและพัก samples ใน SQLite แต่ tracker / point-passage state
  ยังอยู่ในหน่วยความจำ ไม่มี checkpoint/resume และไม่มี Parquet append ที่ปลอดภัยหลัง process ล้ม
- `reid/workflow.py` อ่านตาราง detections / frames และเปิดวิดีโอเพื่อสกัดภาพใหม่เมื่อเริ่มงานจับคู่ใหม่
  มีภาพตัวอย่างและ embedding ในผลเดิมแล้ว แต่ยังไม่มี cache กลางที่นำกลับมาใช้กับงานใหม่ได้
- มีเพดาน 5,000 vehicles ต่อ observation, 10,000 passages/sightings และ 200,000 candidate comparisons
  งานหลายชั่วโมงอาจชนเพดานได้ แม้มีคู่ที่คนต้องตรวจเพียงบางส่วน
- มีการยืนยัน/ปฏิเสธคู่และ shared-track / independent matching อยู่แล้ว
  ต้องต่อยอดการตรวจคู่เดิม ไม่สร้างระบบยืนยันซ้ำอีกชุดหนึ่ง

## ลำดับพัฒนาและเกณฑ์รับงาน

### 1. จัดการชุดคลิปและเวลาถ่ายจริง

- เพิ่มตัวช่วยนำเข้าทั้งโฟลเดอร์และแสดงรายการก่อนบันทึก พร้อม natural sort
- ให้เลือกแหล่งเวลา: รูปแบบวันเวลาในชื่อไฟล์, metadata ที่ตรวจสอบได้ หรือเวลาเริ่มที่ผู้ใช้กรอก
  ระบุ timezone และที่มาของเวลาแต่ละไฟล์ชัดเจน ไม่ใช้ filesystem modified time เป็นเวลาถ่ายโดยอัตโนมัติ
- เมื่อไม่มีเวลาถ่ายจริง รองรับกรอกช่วงห่าง 10 นาทีเป็นข้อสมมุติที่แสดงให้ตรวจทาน
  ไม่อ้างว่าตรวจพบคลิปขาดได้แน่นอนจากชื่อไฟล์ที่ไม่มีข้อมูลเวลา
- สร้าง timeline แสดงช่วงที่บันทึกจริง ช่องว่าง เวลาซ้อน และไฟล์ซ้ำ
  แยกไฟล์ชื่อซ้ำออกจากไฟล์เนื้อหาซ้ำด้วย fingerprint; ตรวจความละเอียดและไฟล์อ่านไม่ได้ด้วย
- เก็บวันเวลาเริ่มจริงแยกจาก PTS ภายในคลิป ไม่บีบช่องว่างให้หายไป
  เมื่อแก้เวลา ให้คำนวณรายงานความครอบคลุมและสถานะความพร้อมใหม่
- ใช้การตรวจไฟล์ในงานเบื้องหลังและ cache ผล probe เพื่อไม่ให้หน้าจอค้าง

เกณฑ์รับงาน: นำเข้า 96 คลิปได้โดยไม่ต้องตั้งเวลาทีละไฟล์ ทดสอบชื่อเรียงผิด คลิปขาด
เวลาซ้อน ข้ามวัน ชื่อภาษาไทย และกรณีไม่มี timestamp โดยไม่เลื่อนเวลาของไฟล์อื่นเพื่อปิดช่องว่าง

### 2. บันทึกความคืบหน้าและทำงานต่อได้

- เพิ่ม run journal และสถานะรายคลิป: รอทำ / กำลังทำ / บันทึกสำเร็จ / มีปัญหา
  แยกปุ่มพักงาน ออกจากยกเลิก และมีหน้ารายการงานที่ทำต่อได้หลังเปิดโปรแกรมใหม่
- ใช้ผลเป็นชิ้นตามคลิปพร้อม journal แทนการเปิด Parquet เดิมแล้ว append หลัง crash
  เขียนชิ้นผลชั่วคราว ปิดและตรวจความสมบูรณ์ แล้วจึง commit checkpoint ให้เป็นชุดเดียวกัน
  ไฟล์ที่ค้างก่อน commit ต้องถูกละเลยหรือสร้างใหม่ ไม่ถูกนับเป็นผลสำเร็จ
- checkpoint ต้องเก็บ clip/frame cursor, frame/detection counters, tracker history และ next ID,
  passage-side history และ next passage ID, stage และตำแหน่งผลที่ commit แล้ว
  เก็บ state แบบมี schema/version ไม่ใช้ pickle
- resume ต้องตรวจ fingerprint ของวิดีโอ config, ROI/จุดผ่าน, calibration, model และ engine version
  หากเปลี่ยนข้อมูลสำคัญ ให้แยกงานใหม่แทนการใช้ผลเก่าปนกับผลใหม่
- รุ่นแรก commit เมื่อจบแต่ละคลิป ทำซ้ำเฉพาะคลิปที่ยังไม่ commit หากหยุดแบบบังคับ
  เก็บสถานะก่อนคลิปนั้นเพื่อให้การเล่นซ้ำคืน track/passage IDs และไม่สร้างเหตุการณ์ซ้ำ
  การ finalization ต้องทำต่อได้เช่นกัน ไม่เขียนตารางรายคันหรือเส้นนับซ้ำ
- tracker ต่อผ่านรอยต่อได้เมื่อข้อมูลและช่วงเวลายังรองรับ เมื่อมีช่องว่างเกินเกณฑ์ต้องหมดอายุตามจริง
  การจับคู่ระยะหลายนาที/ชั่วโมงยังใช้ independent Re-ID ไม่ยืดอายุ Track ID เพื่อบังคับว่าเป็นรถคันเดียวกัน
- รวมผลที่ commit แล้วเป็น Parquet รูปแบบที่ ResultStore เดิมอ่านได้เมื่อจบงาน
  สถานะผลบางส่วนต้องไม่กลายเป็น completed เพียงเพราะเปิดไฟล์ได้

เกณฑ์รับงาน: รันรวดเดียวเทียบกับพัก/ปิด/ฆ่า worker แล้ว resume ได้ข้อมูลและเหตุการณ์เทียบเท่า
ในชุดทดสอบควบคุม ไม่มี ID ซ้ำ ไม่มีข้ามเฟรมที่ยังไม่ commit และไม่ประมวลผลคลิปที่ commit แล้วซ้ำ
ทดสอบ crash ก่อน/หลัง commit และระหว่าง finalization รวมทั้งเปลี่ยนโมเดล/ไฟล์ก่อน resume

### 3. สกัดข้อมูลรถครั้งเดียวและใช้ซ้ำ

- สร้างดัชนี frame / track / passage / เวลาบนดิสก์ เพื่อค้นหาเฉพาะจุดสังเกตที่เลือก
  ไม่โหลดรถทุกคันของ run ก่อนกรอง point gate
- จัดภาพตัวแทนตามลำดับคลิปและ PTS เพื่อใช้ decoder ต่อเนื่อง ลด seek กลับไปมา
  รวมการอ่านเฟรมเดียวกันที่รถหลายคันใช้ร่วมกัน ภายใต้งบหน่วยความจำที่กำหนด
- cache ภาพรถและ embedding แบบถาวร ผูกกับ source fingerprint, frame PTS, full-frame bbox,
  sample selection, model SHA-256, preprocessing และ runtime profile
  เก็บภาพสำหรับคำนวณโดยไม่ให้ JPEG preview เปลี่ยน input ของการสกัด embedding ภายหลัง
- ปรับช่วงเวลา similarity หรือจำนวน Candidate ได้โดยใช้ features เดิม
  เปลี่ยน Re-ID model ให้คำนวณเฉพาะ embedding ส่วนที่จำเป็น ไม่รัน YOLO ใหม่
  เปลี่ยน detector/ROI เป็นคนละรุ่นผลวิเคราะห์ ไม่ย้ายผลยืนยันเดิมไปใช้โดยอัตโนมัติ
- ตรวจ cache เสียหรือไม่ตรง provenance แล้วคำนวณใหม่เฉพาะรายการนั้น
  มีขนาด cache และคำสั่งล้าง cache โดยไม่ลบผลวิเคราะห์หรือผลตรวจยืนยัน

เกณฑ์รับงาน: rerank ด้วยเกณฑ์ใหม่ไม่เรียก YOLO/decoder/Re-ID ซ้ำเมื่อ cache ถูกต้อง
cache เสียไม่สร้าง embedding ผิด และ cache hit/miss ตรวจสอบได้จาก log

### 4. จับคู่เข้า–ออกทั้งวันและรองรับข้อมูลจำนวนมาก

- เพิ่ม preset งานโครงการ: A = ทางเข้า, B = จุดสังเกตทางออกร่วม
  ตั้งช่วงสังเกตตามวันที่จริงและค้นหาคู่ได้หลายชั่วโมง โดยใช้ช่วงเวลาที่ผู้ใช้กำหนด
- ใช้ independent matching เป็นค่าเริ่มต้น เก็บแต่ละ passage เป็นคนละเหตุการณ์
  รองรับเข้า–ออกหลายรอบ ป้องกันการใช้เหตุการณ์ออกเดียวกันยืนยันให้รถเข้าสองเหตุการณ์
- เพิ่มการค้นหาที่แบ่งตาม point / class / เวลา และคำนวณ similarity เป็น block
  ไม่สร้างตาราง N×M ทั้งหมดใน RAM และไม่แก้ปัญหาด้วยการเพิ่มเพดานตัวเลขเดิมเท่านั้น
- บันทึก candidate scores ลงดิสก์และแสดง top-K แบบแบ่งหน้า พร้อม “ค้นหาเพิ่ม”
  ระบุให้เห็นเมื่อยังมีคู่ที่ไม่แสดงหรือค้นหาไม่ครบ ห้ามเปลี่ยน top-K เป็นข้อสรุปว่าไม่มีคู่
  หากเพิ่ม approximate index ต้องวัด Recall@K เทียบวิธี exact ก่อนใช้เป็นค่าเริ่มต้น
- คง one-to-one assignment เป็นคำแนะนำและใช้ผลคนยืนยันเป็นข้อจำกัด
  rerank ต้องเก็บประวัติการยืนยันเดิม และแจ้งกรณีเงื่อนไขใหม่ขัดกับคู่ที่เคยยืนยัน
- ใช้ Vehicle Re-ID ONNX ที่เข้ากับ input contract และวัดกับภาพหลายมุม/กลางวัน/เย็นจริง
  histogram สีคงไว้เป็น baseline ที่ระบุชัด ไม่อ้างว่าการเปลี่ยนโมเดลจะทำให้แม่นยำถึงเป้าหมายทันที

เกณฑ์รับงาน: ชุดข้อมูลจำลองที่เกินเพดานเดิมทั้ง 5,000 รถ, 10,000 เหตุการณ์
และ 200,000 การเปรียบเทียบทำงานได้ภายใต้งบทรัพยากรที่กำหนด พร้อม cancel/progress
ผลชุดเล็กต้องตรง exact reference และการเลือก top-K ต้องตรวจอัตราพบคู่จริงได้

### 5. หน้าตรวจยืนยันและรายงานที่ตีความถูกต้อง

- แสดงภาพหลายตัวอย่าง เวลาเข้า/เวลาที่พบ B คลิปต้นทาง คะแนน ความกำกวม และอันดับคู่
  เปิดดูวิดีโอเต็มก่อน–หลังเหตุการณ์ได้ และกลับมาทำคิวตรวจต่อหลังเปิดโปรแกรมใหม่
- แยก “ยืนยันรถคันเดียวกัน” ออกจากหลักฐานว่า “ออกจากประตูโครงการโดยตรง”
  จุด B หลังทางรวมต้องระบุว่าเป็นเวลาผ่านจุดสังเกต ไม่ใช่เวลาออกประตูจริงหรือเวลาจอดจริง
- รายงานแยก: คู่ยืนยันแล้ว / รถเข้าที่ยังไม่พบคู่ / รถที่ B ซึ่งยังระบุต้นทางไม่ได้ / รอตรวจ
  แสดงจำนวนเหตุการณ์กับจำนวนรถที่ยืนยันตัวตนเป็นคนละรายการเมื่อมีการกลับมาหลายรอบ
- แนบช่วงวิดีโอขาด การตรวจจับที่ยังไม่ประมวลผล และสถานะความครบถ้วนของการตรวจคู่
  ก่อน 06:00 / หลัง 22:00 เป็นเพียงสาเหตุที่เป็นไปได้ของรถไม่มีคู่ ไม่ใช่ป้ายข้อเท็จจริงอัตโนมัติ
- ส่งออก CSV พร้อม full-frame coordinates, provenance, รูปแบบหลักฐาน และ review history
  ไม่สรุปรถไม่มีคู่เป็นรถจากซอย และไม่ใช้จำนวนคู่แทนรถออกทั้งหมดหรือรถคงเหลือในโครงการ

เกณฑ์รับงาน: ตรวจชุดตัวอย่างที่มีรถเดิมหลายรอบ รถเหมือนกัน รถเข้าก่อนช่วงสังเกต
รถออกหลังช่วงสังเกต และรถซอยปะปน ตัวเลขทุกกลุ่มตรวจย้อนกลับถึงเหตุการณ์และผลคนยืนยันได้

### 6. ทดสอบความเร็วและแจกโปรแกรมสำหรับทดสอบ

- เก็บ baseline ก่อนแก้แต่ละเฟส: เวลารวม decode/detect/features/matching, FPS,
  RAM/VRAM สูงสุด, พื้นที่ดิสก์ และจำนวนภาพที่คนต้องตรวจ
- เปรียบเทียบ CPU/GPU และ full-frame/ROI บนเครื่องและวิดีโอเดียวกัน
  คง full-frame output, PTS, wheel guard และ road calibration ที่มีอยู่
  ไม่ลด FPS ตรวจจับหรือเลือก sample ให้น้อยลงโดยไม่มีการวัดรถตกหล่น/เวลาผ่านจุด
- ชุด CI ใช้คลิปสั้นจำนวน 96 ไฟล์และไทม์ไลน์จำลองร่วมกับการทดสอบรอยต่อ/ช่องว่าง
  ส่วนการยืนยันความจุและเวลาทำงานตลอด 16 ชั่วโมงใช้วิดีโอจริงบนเครื่องเป้าหมาย
- วัดความถูกต้องด้วยรถที่คนตรวจไว้ แยกชุดปรับเกณฑ์ออกจากชุดทดสอบ
  รายงาน detection recall, precision ของคู่, Recall@K, จำนวนรถไม่มีคู่ และภาระการตรวจของคน
  ไม่ประกาศเปอร์เซ็นต์ความแม่นยำหรือเวลาเสร็จก่อนมี benchmark บนข้อมูลจริง
- ให้ GitHub Actions สร้าง Windows CPU/CUDA พร้อม frozen inference, GUI/worker smoke
  และทดสอบ workflow นำเข้าคลิป–พัก–ทำต่อ–ตรวจคู่–ส่งออก ก่อนแนบ ZIP ให้ดาวน์โหลด

## ชุดส่งมอบ

1. ชุดแรก: เฟส 1–2 — นำเข้าทั้งวันและทำงานต่อได้ พร้อมชุดทดสอบ Windows
2. ชุดที่สอง: เฟส 3–4 — cache และการค้นหาคู่จำนวนมาก ปรับเกณฑ์ซ้ำได้รวดเร็ว
3. ชุดที่สาม: เฟส 5 และการตรวจรับเฟส 6 — หน้าตรวจคู่ รายงานความครบถ้วน และ benchmark ภาคสนาม

ทุกชุดต้องรักษาการอ่านผลเดิม หรือมี migration ที่เก็บต้นฉบับไว้
เกณฑ์ทดสอบของแต่ละเฟสเป็นเงื่อนไขก่อนส่งชุดนั้น ไม่รอทดสอบทั้งหมดในเฟสสุดท้าย

ข้อมูลที่ช่วยกำหนด implementation โดยไม่ขวางการวางแผน:
ชื่อไฟล์ตัวอย่าง 2 ชื่อเพื่อกำหนด timestamp parser, ความละเอียด/FPS, รุ่น GPU/RAM
และตัวอย่างคู่รถที่คนยืนยันแล้วสำหรับวัดความแม่นยำ รูปแบบที่ยังไม่ทราบใช้การตั้งค่าโดยผู้ใช้แทนการเดา
